この記事では、いまのブログを Void と Cloudflare で作り直す計画と、その計画で決めたことを書きます。作るのはこれからなので、まだ動くものはありません。

## いまの構成と、変えたいところ

いまのブログは FUNSTACK Static で作っています。ビルドのときに全ページを HTML にして、Vercel に置くだけの静的なサイトです。記事は `content/posts/*.md` を直接編集して、Git に push して公開しています。

この構成はよくできていて、困ってはいません。それでも変えたいのは、記事の書き方です。

- ブラウザの管理画面から、自分だけがログインして記事を書きたい
- 書いている途中で、その場でプレビューを見たい
- 記事は DB に持ちたい。ただし Markdown でも配信したい

今の構成のままでも、ローカルで `pnpm dev` を動かせばプレビューはできます。ただ、スマホから思いついたときに書く、ということができません。記事を DB に置いて、ブラウザから書ける形にしたくなりました。

## Void は何者か

きっかけは、azukiazusa さんの [Void で Vite のアプリを Cloudflare にデプロイする記事](https://azukiazusa.dev/blog/void-vite-cloudflare-deploy) でした。

Void は Vite をベースにしたフルスタックの SDK で、Cloudflare Workers の上で動きます。GitHub の [voidzero-dev/void](https://github.com/voidzero-dev/void) で公開されていて、ドキュメントも同じリポジトリに入っています。私が実際に読んで、使えそうだと思った点は次のとおりです。

- `pages/` に React のコンポーネントを置くとルートになり、隣の `*.server.ts` にデータを取る `loader` を書けます
- D1 や R2 は、コードから使っているものを読み取って、デプロイのときに自動で用意されます
- Better Auth が設定済みで入っていて、GitHub のログインを数行で足せます
- ページを一定時間キャッシュして、記事を公開したときに指定したページだけ無効化できます

管理画面も、公開側のページも、API も、1つのプロジェクトに収まりそうです。

## 決めたこと

計画は Claude と相談しながら、1つずつ選択肢を比べて決めました。理由まで残したかったので、決めたことと却下したことを並べます。

### 記事の正は D1、公開側は D1 を読まない

記事の本体は D1 に置きます。ただし、読者がページを開いたときは D1 に触りません。

理由はお金です。D1 は読み取った行数と書き込んだ行数で課金されるので、全件を舐めるクエリや急なアクセス増で、請求が思わぬ額になることがあると聞きました。そこで、D1 を使うのは管理画面だけにします。公開するたびに、読者向けの記事データ、検索インデックス、RSS、OG 画像を R2 に書き出しておき、公開側のページはそれだけを読みます。

記事の `.md` ファイルも、公開のときに R2 に保存します。これが `/posts/<slug>.md` で配信するファイルであり、バックアップにもなります。

リポジトリのファイルを正にして、D1 は写しとして使う案も考えました。ですが、ブラウザから書くのに、保存のたびにコミットが要るのは筋が悪いので外しました。

### Markdown のパーサーは自作する

いまは ox-content という、Rust で書かれたパーサーを使っています。ネイティブのバイナリなので、Workers の上では動きません。

remark などの JavaScript 製のパーサーに乗り換える手もあります。ただ、せっかくなので TypeScript で自作することにしました。自作すれば、サーバーとブラウザで同じコードが動きます。管理画面のプレビューと、公開された記事の見た目がずれる心配がなくなります。

作る範囲は小さくします。既存の 25 本の記事で使っている構文を数えたところ、使っているのは見出し、コード、リンク、リスト、引用、表、画像くらいでした。取り消し線や脚注などは対応しません。対応しない構文が書かれたら、黙って無視せずに、エラーとして知らせます。

### プレビューにはエラーを出す

書いている途中の記事は、壊れていても保存できるようにします。保存を拒否すると、書きかけが消えるのが怖いからです。

その代わり、プレビューには検証の結果を出します。frontmatter の抜け、危険な URL、見出しの飛び、未対応の構文を、行番号つきで並べて、クリックすると該当の行に飛べるようにします。エラーがあるうちは、公開ボタンを押しても公開できません。

### 認証は GitHub ログインだけ

ログインできるのは自分だけなので、メールとパスワードの仕組みは作りません。Void に入っている Better Auth のソーシャルログインを GitHub で使い、自分のアカウント以外は入れないようにします。

Cloudflare Access で管理画面ごと守る案もありました。コードは減りますが、ローカルの開発では認証が効かないので、今回は見送りました。

### 見た目が変わっていないことは、スクリーンショットで確かめる

作り直しで一番怖いのは、気づかないうちに見た目が崩れることです。そこで、移行する前の今のサイトで、スクリーンショットを撮って残しておきます。Vitest のブラウザモードと `toMatchScreenshot` を使います。

作り直したあとのサイトに同じテストを向けて、差が出ないことを確かめます。25 本の記事すべてを撮るので、自作したパーサーが正しく動いているかの確認にもなります。

## 進め方

本番は、切り替えの日まで今のままにしておきます。作業は統合ブランチを1本切って、そこを土台にして、フェーズごとの PR を `gh stack` で積んでいきます。`gh stack` は GitHub が出している、PR を積み重ねるための公式の拡張です。

| フェーズ | やること                                                    |
| -------- | ----------------------------------------------------------- |
| 0        | 動くかを確かめる実験 (Void のデプロイ、WASM の OG 画像など) |
| 1        | 今のサイトのスクリーンショットを撮る                        |
| 2        | Markdown のパーサーを作る                                   |
| 3        | Void を入れて、FUNSTACK を外す                              |
| 4        | 記事を公開する処理と、公開側のページ                        |
| 5        | ログインと管理画面                                          |
| 6        | OG 画像と、既存記事の取り込み                               |
| 7        | 見た目と URL を、移行前と突き合わせる                       |
| 8        | ドメインを Cloudflare に切り替える                          |
| 9        | ドキュメントを直す                                          |

計画の全文は、リポジトリの `docs/void-cloudflare-rebuild.md` にあります。

## まだ分からないこと

不安なところも、正直に書いておきます。

- Void は 2026 年 10 月に公開されたばかりで、仕様が変わる可能性があります。今回は、バージョンを固定せずに最新を追いかけることにしました。その代わり、スクリーンショットのテストと型チェックを、移行したあとも回し続けます
- OG 画像の生成が、Workers の上で時間とメモリの制限に収まるかは、やってみないと分かりません。ダメなら別のライブラリに替えます
- 画像を WebP に変えるのを、ブラウザでやるか、サーバーでやるかも未定です

## おわりに

ここまで決めてから作り始めます。作りながら、ハマったところはこのブログに書いていきます。

作り直しが終わると、この記事も、管理画面から書いたものに置き換わっているはずです。
